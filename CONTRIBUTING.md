# Contributing to SkillArc

## From issue to handoff

GitHub Projects is the sole active tracker. Use the issue for agreed behavior and decisions, and the PR for the change, review, and evidence. Jira references are historical.

1. **Pick up the issue.** Read its latest comments, linked PRs, dependencies and Project status. Use the human-agreed task owner recorded on the issue and check the repository's delivery requirements below. Confirm the user outcome, scope, acceptance criteria and finish line in your own words. Ask the humans to resolve missing ownership, conflicting behavior or a material scope decision. Record the agreed choice, why it was made and what it affects in the issue.
2. **Agree on cross-repo behavior.** Link the server and mobile issues in both directions and name the dependency. Keep private source, artifacts and implementation details out of public records. Agree on the canonical server OpenAPI revision and synthetic examples for success, empty, denied and error cases that apply. Verify the deployed server revision on staging before updating the mobile contract snapshot. Record the deployed commit, verification run and any remaining dependency on the issues or PRs.
3. **Implement and publish.** Start a dedicated branch from current `staging`. When authorized to publish, push the agreed scope and open an early draft PR targeting `staging`. Link one issue from the same repo with a `GitHub issue: #<number>` line. Link the companion issue/PR where relevant. Use existing code and checks, keep the diff focused, and reproduce a bug and verify the fix at the affected surface when feasible.
4. **Verify and respond to review.** Run the applicable checks below. In the PR, record AI assistance, the commit tested, commands and results, what the author verified personally, and any pending evidence. Distinguish local verification, CI, merged code and staging verification. Make review fixes on the existing branch, reply with the fix or evidence, and get independent approval of the latest head after pushing fixes. Resolve review conversations before merging.
5. **Merge or hand off.** Merge only when authorized to merge, after independent approval of the latest head, passing required checks and any applicable release gates. Squash feature PRs. Leave the issue or PR with the verified state, remaining blocker or decision, and a named next owner and action. Keep the Project status aligned with the agreed finish line.

## Server delivery requirements

- Check the [review policy](scripts/ci/review-policy.mjs). The current gate requires `@keanesc` on the linked delivery issue. If another approved contributor authors the PR, GitHub must also list that contributor as an assignee. Record who owns the task in the issue so Keane's required assignment does not imply ownership. All delivery PRs require latest-head approval by `@lumbinitechnologies`. Use your own account. Never approve your own PR through an owner account.
- Use `<contributor>-<issue>-<description>` for a feature branch, for example `keane-108-agent-handoffs`. Use plain-language titles and preserve historical Jira references. Rebase on current `staging` before review if needed. Only use `git push --force-with-lease` on your own branch.
- Run `npm run lint`, `npm run typecheck` and `node scripts/ci/server-tests.mjs` for server changes. When changing database behavior, use the migration-history guards, full local replay, database tests, lint and security advisors in [database delivery](docs/DATABASE_DELIVERY.md). Use the smallest check that verifies each acceptance criterion and run the required CI gates. Report any baseline failure and its impact.
- For mobile API changes, use the [canonical OpenAPI](contracts/mobile-v1.openapi.yaml) and [student academic examples](docs/react-native-port/contracts/student-academic-examples.json). Use synthetic fixtures. Keep private artifacts, credentials and real student data out of issues and PRs.

## Release and exceptions

- Release PRs promote `staging` to `main` with a merge commit. Link a release issue with included work and evidence. Production candidates must match the tested staging tree and receive human owner approval through the applicable protected release workflow. For the combined release, bind approval to the exact website and signed Android candidate. Keep mobile source, signing secrets and APKs private. A passing PR does not authorize a new integration, secret, purchase, resource retirement or production release.
- Branch urgent fixes from `main` as `keane-hotfix-<issue>-<description>` under the current policy. Apply the same checks and review, then immediately open a reviewed merge back to `staging`.
- Trusted review workflows run protected base code and never execute PR scripts with write tokens. Dependabot may skip the linked issue for manifest, lockfile or workflow action-version changes that receive Keane's latest-head approval.
- Follow [database delivery](docs/DATABASE_DELIVERY.md) for migration and activation gates, including [issue #67](https://github.com/lumbinitechnologies/skillarc/issues/67). Preserve applied baseline SQL. Keep automatic history repair, hosted resets and production seeds out of the delivery workflow. Use the approved database parent, isolated staging/PR branches and hosting targets in the delivery configuration.
