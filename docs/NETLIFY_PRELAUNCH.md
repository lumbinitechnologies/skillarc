# Netlify website prelaunch

Track preparation in #101 and the public release in #96. The separate mobile launch policy and existing Vercel workflow still apply to their respective release paths.

## Prepare a private draft

1. Keep the Netlify project unlinked from Git and require team sign-in for all deploys. Leave its primary hostname and custom domains unpublished during preparation. Confirm the team is on Free, quota is available, and it has no paid recharge.
2. Independently review the code on `staging` and require a successful hosted staging run after merge. Use the reviewed staging-to-main merge with the same Git tree for the release candidate. Keep the exact-review and production environment checks in `verify-release.mjs`.
3. Configure the `skillarc-netlify-candidates` GitHub environment for `main`, using an owner-approved deployment credential and only the clean production ref and its publishable key as settings. Enable `NETLIFY_PRELAUNCH_PREPARE_ENABLED` only when candidate preparation is approved. Dispatch **Prepare private Netlify prelaunch candidate** with the reviewed main SHA. This workflow only creates a protected draft. The record binds the exact revision, hosted staging evidence, configuration, migration digest, Netlify project and deploy. Keep the record with the release evidence.
4. Open the exact draft while signed in to Netlify. Verify the six public pages and their assets, the closed portal, signup and mobile routes, and the closed admissions and worker APIs. Check the same origin anonymously and require Netlify sign-in. Exercise the blocked write routes with synthetic requests against a staging rehearsal and verify before and after that no account, application, payment or background activity was created. Use the smoke tests in `scripts/ci/prelaunch-smoke.mjs` as the baseline. A local rehearsal record is supporting evidence.

Prelaunch is built into the artifact. The build uses a publishable key, with no service-role key, payment, SMTP or job credentials. Netlify deploy metadata must report zero scheduled functions. Review the final config and the inherited project and team settings before the public release.

## Prepare the database and fallback

- Reconfirm the clean production ref, the exact bootstrap migration-history row, its statement digest, application schema and zero account/file counts. Present the recommendation in #96. After separate approval of the history correction, verify the revised ledger and aggregate counts, then dry-run the reviewed migrations with zero seeds and roles. The explicit `apply_migrations` input is disabled by default. For an approved database release, set `NETLIFY_PRELAUNCH_MIGRATIONS_ENABLED`. Supply the exact immutable fallback deploy ID. The workflow builds a private candidate and displays its digest before the existing production approval gate. Independently verify the private candidate and fallback before approving the production job. After approval it checks the exact candidate, fallback, code, staging run and production configuration again, then verifies the exact dry run, applies without seeds or roles, and rechecks the ledger and empty production data. This workflow is scoped to the database and private drafts.
- Verify that direct Supabase Auth signup and anonymous access are disabled and there is no custom SMTP. Check the production project settings directly because the website guard only covers requests to the website. The production job needs the same project ref and publishable key as the candidate environment, a Netlify credential for metadata checks, and the separately scoped Supabase and GitHub policy credentials. Verify the required empty private buckets and zero legacy data after approved migrations.
- Keep a separate tested Netlify artifact that serves the informational site with onboarding closed and no dependency on either database. Record its deploy ID, source and how to reproduce it before the draft expires. Verify the planned recovery path under the applicable project visibility and DNS settings before setting a switch date. The currently live Vercel site serves a sign-in form and is unsuitable as the onboarding-closed fallback. Recover the application by serving a fresh deploy of the rehearsed fallback; keep the production database unchanged during an application recovery.

## Public switch and verification

Bring the exact candidate ID, fallback ID, clean production binding, migration dry run, GitHub review and hosted staging run to the owner as one release record. The domain change and exact Netlify publication require public switch approval. If the platform requires a fresh production deploy, keep it private and rebind and retest the exact new deploy before routing visitors.

Retain the existing DNS provider. Before authorized DNS changes, export the zone and recheck the records. Change only the apex and `www` records to the project-specific values in Netlify, preserving staging, MX, TXT and other records. Verify certificate coverage for both public names and the apex-to-`www` redirect. Account for the DNS TTL and certificate provisioning during the switch. Use Netlify's [external DNS instructions](https://docs.netlify.com/manage/domains/configure-domains/configure-external-dns/) and the project dashboard for the pending verification details.

After the switch, check the exact published deploy identity, the public pages and assets, the closed routes, and the staging API. Verify that the new website and the fallback still work without the legacy project. Retention, recovery testing of the actual legacy archive, and deletion are tracked separately.
